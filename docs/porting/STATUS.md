# Porting status — anthropic (Python) 2.3.0 → Swift

Everything in the upstream SDK is either generated by the transpiler or ported by hand, with its tests.
`swift test` runs ~3,800 tests (1,574 generated from `tests/api_resources`, the rest hand-ported).
Per-area details, including every upstream test that was skipped and why, are in the files linked below.

## Deliberate differences

* One async client instead of sync + async twins.
* `X-Stainless-Lang: swift` and a Swift user agent in telemetry headers.
* Responses are decoded strictly into typed models (unknown enum values and union variants are kept via
  `unknown(...)` cases; unknown object keys are dropped). Python's non-strict `construct` leniency for
  missing required fields has no equivalent for a response. A stream is read leniently instead
  (`LenientStreamEvent`: the Messages and Sessions event unions): an event of a known type that does not decode (a
  `null` where a number was expected, a required key left out) is handed out as the union's `unknown` case holding its
  JSON, and the stream goes on, as upstream's `construct_type` and the TypeScript SDK's casts let it through. The
  typed `MessageStream` / `BetaMessageStream` still give such a block start its place and take a message delta's stop
  reason, and withhold their snapshot from the call's span (see `tracing.md`).
* Request bodies: Python's dicts keep insertion order, so its bodies are the same bytes on every request. A Swift
  `Dictionary` (and so `JSONValue`) has no order and iterates differently per instance and process, so the request
  pipeline writes a body built from typed params with each object's keys sorted (`BaseClient.serializeBody`): the
  same request is the same bytes in every process, which prompt caching needs. A body given as `RawJSON`
  (`FinalRequestOptions.rawJSONBody`) is written in its own order, with changes made through `jsonData` (middleware,
  platform clients, `extraBody`) folded in by `RawJSON.reconciled(with:)`.
* Verbatim JSON, which the TypeScript SDK has by passing JSON through and Python by keeping unknown fields on its
  models: `RawJSON` is an order-preserving JSON value (document order when parsed, insertion order when built, each
  number's text kept, explicit `null`s kept). `messages.createStreaming(body:)` / `beta.messages.createStreaming(body:)`
  send a `RawJSON` body as it is and return a `JSONMessageStream`, whose events carry their JSON beside the typed
  event (`JSONStreamEvent`) and whose `JSONMessageAccumulator` builds the Message as JSON
  (`_beta_messages.accumulate_event` over JSON: block starts as received, text / thinking / signature / citations /
  compaction deltas applied, `input_json_delta` parts parsed at the block's stop in the model's key order). It is for a
  client that keeps its history as the JSON it received and replays it unchanged.
* An `error` event of a stream raises the typed error of its `error.type` (`OverloadedError` for `overloaded_error`,
  `RateLimitError`, `InternalServerError` for `api_error`, ...), whose `statusCode` is the status the API answers that
  type with (529, 429, 500; `response.statusCode` stays the stream's 200), with `errorMessage` its `error.message`.
  Python raises `APIStatusError` with status 200 for every one; an event with an `error.type` this SDK does not know
  still does.
* Structured outputs use a `StructuredOutput` protocol (a `Decodable` type supplying its JSON schema) instead of
  pydantic schema inference; function tools declare their input schema explicitly instead of inferring it from a
  Python signature.
* No third-party dependencies: crypto (SigV4, Google service-account JWTs, webhooks), gzip/zip/tar reading and the
  OpenTelemetry API are implemented in-tree.
